# Native subscription refund transaction candidate

This is an **unactivated candidate patch for an isolated experiment**, based on New API commit `0aec08fee811ec6136828fda790551b49e410301`. It does not change the running Native binary, deployment defaults, policy approvals, Studio ledger, or any existing account amount. It is not a repair procedure for the recorded QA discrepancy.

## Source evidence and proposed change

[RefundSubscriptionPreConsume](https://github.com/QuantumNous/new-api/blob/0aec08fee811ec6136828fda790551b49e410301/model/subscription.go#L1402-L1426) starts a Gorm transaction, locks/reads a request's pre-consume record, and calls the public `PostConsumeUserSubscriptionDelta`. [That public function](https://github.com/QuantumNous/new-api/blob/0aec08fee811ec6136828fda790551b49e410301/model/subscription.go#L1510-L1533) starts a **different transaction through the global `DB`**, rather than the supplied outer `tx`. Consequently, the subscription amount change and the `refunded` idempotency marker do not share one commit/rollback boundary. On a database allowing the inner transaction to commit, failure of the later outer record update can leave the amount refunded without its marker. On SQLite, the separate connection/transaction also creates a lock-conflict risk. The source proves the broken transaction boundary; the observed QA lock errors alone do not prove which particular request triggered them.

`refund-transaction.patch` extracts the existing amount-update body into a private `postConsumeUserSubscriptionDeltaTx(tx, subscriptionID, delta)` helper. Refund uses its existing transaction for record lock, subscription lock/change, and record status update. The public function keeps its validation, zero-delta no-op, independent transaction, amount clamp and upper-limit behavior. No retries are added.

The full fixed-source call-site review found the nested call in `RefundSubscriptionPreConsume`; remaining public delta callers are `BillingSession.Refund` (extra reserve), `reserveFunding`, `rollbackFundingReserve`, `SubscriptionFunding.Settle`, `postConsumeQuotaWithResult`, and `taskAdjustFunding`. These service callers do not hold a Gorm transaction, so their public transaction boundary is retained. The only refund caller is `SubscriptionFunding.Refund`. `model/locking.go` omits `FOR UPDATE` on SQLite and uses a row-lock clause on other databases. Regression execution must be recorded before approving a candidate binary.

## Cache and safety boundaries

These two amount/refund functions do not update a subscription amount cache. `SubscriptionPlanInfo` caches only `PlanId` and `PlanTitle`; the plan cache contains plan metadata. The patch does not invent cache invalidation for `AmountUsed`. Other subscription payment/admin/expiry transactions perform wallet/group cache refresh after a successful database transaction; these paths remain unchanged. A future cache addition must publish or invalidate after the complete refund transaction commits, never after only an inner amount write.

Refund remains a trusted internal request-ID operation. It derives the target subscription from its persisted pre-consume record, rather than accepting a client-supplied owner or subscription. This does not add public refund authorization. Existing pre-consume request-ID reuse does not compare the caller's owner to the stored record's owner; request-ID generation/trust remains an upstream boundary and is not broadened by this patch. Regression tests must verify that unrelated owners/subscriptions remain unchanged.

This candidate does not make Native funding and token refund one transaction. `BillingSession.Refund` still runs asynchronously and refunds funding before token quota; either can fail separately. It does not make HTTP failure proof of a refund, add durable retry workers, settle old unknown Studio reservations, solve delayed refunds across subscription resets or deleted pre-consume records, or prove provider procurement costs. Existing QA failed history and unknown reservations must remain intact.

It adds the original positive-ID validation to the private helper and a persisted invalid-ID regression within the existing six tests. The final isolated Native HTTP case also passed with matching frozen patch, binary and image identities. The complete source checkout reports HEAD `0aec08fee811ec6136828fda790551b49e410301`; its original `model/subscription.go` matches the inspected flattened source (`c233eafac976f3d2fc3d61332666270903947561bd5b6f112086be28ae301dab`). Clean-source `git apply --check` and repository `git diff --check` passed. The ignored local generator is preparation tooling, not a deployment tool.

The patch includes six `TestRefundTransaction*` regressions executable against SQLite, MySQL, and PostgreSQL. They cover four available connections; normal refund and duplicate refund; rollback of both subscription amount and marker when the record update fails; rollback when the subscription update fails; concurrent duplicate refund; unrelated owner isolation; missing request/subscription and zero reservation; and unchanged public delta upper-limit/zero-delta/clamp behavior. Marker failure is injected by a Gorm update callback **after reading the already changed amount through the actual transaction**, followed by external reads proving both writes rolled back. No transaction is mocked. On MySQL/PostgreSQL both concurrent calls must return nil with one refund effect; SQLite alone may return a lock error for the losing writer, followed by an explicit idempotency check.

The test restores the global DB/type and does not run in parallel with other model tests. Each test creates and drops only its two tables with a unique `refund_test_*` prefix, registering cleanup before migration. Native's explicit `idx_user_sub_active` model tag remains unchanged: PostgreSQL index names are schema-wide, so the required empty isolated database and serial cleanup matter; a table prefix alone is not an assurance against index collisions in an existing schema. External database DSNs must point to the operator's new isolated test databases; never supply QA, main, or production database connections. DSNs and passwords are not logged.
